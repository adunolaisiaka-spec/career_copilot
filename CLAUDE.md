# CLAUDE.md — Master Configuration

This file is the master configuration for this project. Claude Code reads it at the start of every session to understand how work here is organized, where things live, and how to behave before taking any action.

This project is organized around the **WAT Framework**: **W**orkflows, **A**gent, **T**ools.

## The WAT Framework

### W — Workflows

Workflows are step-by-step procedure files that orchestrate the work. Each workflow lives in `/workflows/` as a markdown file describing a repeatable task from start to finish: what inputs it needs, the ordered steps to follow, which tools to call at each step, and what the final output should look like.

Workflows are the "recipes" of this project — they don't contain implementation code themselves, they describe _when_ and _in what order_ to call the scripts in `/tools/`.

### A — Agent

Claude Code is the agent. The agent's job is to read a workflow, follow its steps in order, decide which tool to invoke at each step, handle errors or missing information sensibly, and produce/save the expected output.

The agent should always prefer an existing workflow or tool over improvising from scratch. Before starting an ad hoc task, check `/workflows/` for a matching procedure and `/tools/` for a script that already does what's needed.

### T — Tools

Tools are the scripts and integrations the agent uses to actually get things done — web scraping, API calls, file generation, data transforms, third-party integrations (e.g. Firecrawl), etc. Each tool lives in `/tools/` and should be small, focused, and reusable across multiple workflows.

Tools do the work; workflows decide when to call them; the agent drives the whole process.

## Folder Structure

```
career-copilot/
├── CLAUDE.md              # this file — master config, read every session
├── .env                   # API keys/secrets (never committed)
├── .gitignore
├── workflows/             # step-by-step procedure files (.md)
├── tools/                 # scripts and integrations the agent calls
└── temp/                  # temporary working files
    ├── output/            # generated outputs (briefs, reports, docs, etc.)
    └── resources/         # scratch/downloaded resources used mid-workflow
```

- **`/workflows/`** — One markdown file per repeatable procedure. Name files after the task they perform (e.g. `research-brief.md`). New workflows go here.
- **`/tools/`** — Scripts and integrations (e.g. a Firecrawl scraper, an API client). New tools go here.
- **`/temp/output/`** — Where finished, generated artifacts are written (final reports, briefs, documents). Never write final outputs to the repo root.
- **`/temp/resources/`** — Scratch space for intermediate/downloaded files used while a workflow is running (raw scrape results, drafts, working notes).
- **`.env`** — All API keys and secrets live here as environment variables. It is listed in `.gitignore` and must **never** be committed, printed to logs, or pasted into workflow/tool files. Tools and workflows must read secrets via environment variables, never hardcode them.

## Session Start Behavior

At the start of a session, before doing ad hoc work, the agent should:

1. Check `/workflows/` for an existing workflow that matches the requested task.
2. If a workflow exists, follow it step by step, calling the tools it references.
3. If a step needs a capability that doesn't exist yet, check `/tools/` before writing a new script.
4. Write any generated artifacts to `/temp/output/`; use `/temp/resources/` for intermediate/scratch files.
5. Read required secrets from `.env` / environment variables — never ask the user to paste a key into chat if it's already in `.env`.

## Adding New Workflows or Tools

- **New workflow**: add a new `.md` file to `/workflows/` named for the task it performs. Document: purpose, required inputs, ordered steps, tools used at each step, and expected output location.
- **New tool**: add a new script to `/tools/` with a short header comment describing what it does, its inputs/outputs, and which environment variables (from `.env`) it needs.

Post-deployment fixes: three real bugs surfaced only after the app went live on Vercel — each looked fine in local dev and was only caught by testing directly against the deployed site, not just local/CI runs.
1. **`temperature` param rejected by the model** — every `AnthropicAIService` call (`lib/ai/adapters/anthropic.ts`) passed `temperature`, which `claude-sonnet-5` rejects with a 400 ("temperature is deprecated for this model"). Broke every real AI call the moment a real `ANTHROPIC_API_KEY` was configured. Fixed by removing it from all 7 call sites.
2. **Rate limiting was a no-op in production** — `lib/utilities/rate-limit.ts` was an in-memory `Map`, which resets on every cold serverless invocation. Replaced with a Postgres-backed atomic upsert (new `RateLimitBucket` model/migration) — verified race-safe under concurrent requests. Also had to disable Vitest's file-level parallelism (`fileParallelism: false`) since enough integration suites now exist that running them in parallel workers was exhausting the free-tier Neon test branch's connection limit.
3. **Resume uploads were completely broken**, for two stacked reasons found live: (a) `pdf-parse`/`pdfjs-dist` doesn't run inside a Next.js server bundle — locally it failed on a missing worker chunk, on Vercel it failed with `"DOMMatrix is not defined"` (a browser-only API); replaced with `unpdf`, built specifically for serverless PDF extraction. (b) Once that was fixed, uploads hit a second bug it had been masking: `lib/storage/adapters/local-disk.ts` writes to `process.cwd()/storage`, which is read-only on Vercel outside `/tmp` (`"ENOENT ... mkdir '/var/task/storage'"`). Added a Vercel Blob adapter (`lib/storage/adapters/vercel-blob.ts`, `access: "private"` — never reachable by URL alone, same guarantee as the old auth-gated file route). `getStorageService()` auto-detects Blob via **either** `BLOB_READ_WRITE_TOKEN` (classic static token) **or** `BLOB_STORE_ID` (the newer OIDC-based connection the Vercel dashboard now provisions by default when you connect a Blob store — an identity token the platform auto-injects at runtime, no static token exposed at all); `@vercel/blob` resolves OIDC auth on its own since our adapter never passes a `token` option. **Verified live end-to-end**: uploaded a real resume, got a real AI score (84/100) with content-aware recommendations, confirming extraction + storage + analysis all work together on production.

Also fixed during this pass, not bugs but real gaps: tests now force `AI_PROVIDER=mock` in `tests/setup.ts` regardless of `.env`, since adding a real key locally was silently making "(mock AI provider)"-labeled integration tests hit the real API — non-deterministic and burning real credits.

**Writing the integration/E2E suites caught three more real, previously-undiscovered bugs, all fixed and re-verified**:
1. `lib/validation/job.ts`'s `jobSearchSchema` — the `/jobs` search form's `<select>`/`<input>` fields always submit `""` when left at their default (native HTML form behavior), but `z.coerce.number()` turned that into `0` (failing `.min(1)` on `postedWithinDays`) and `z.enum([...])` rejected `""` outright (on `remoteType`) — either failure made `safeParse()` fail, and `app/jobs/page.tsx` silently fell back to **all-default filters**, discarding every filter the user had actually selected. Fixed with an empty-string-to-`undefined` preprocessing step before the numeric/enum checks.
2. Base UI's `<Select.Value>` (`@base-ui/react/select`, not Radix) only ever displays the raw selected value unless given an explicit value→label mapping function — it does **not** auto-resolve a matching `<Select.Item>`'s rendered label. Every `<SelectValue>` usage in the app (`application-dialog.tsx` status, `goal-dialog.tsx` term/status, `profile-form.tsx` + `onboarding-wizard.tsx` career-level/work-arrangement, `resume-analyzer.tsx` resume picker — 8 usages across 5 files) was showing the raw enum/id instead of its label (e.g. "APPLIED" instead of "Applied"; the resume picker showed a raw cuid instead of the resume's title). Fixed by passing a `children` mapping function to every `<SelectValue>`.
3. `components/applications/kanban-board.tsx`'s `selected` state (the application shown in the edit dialog) was captured once at click-time and never re-pointed at fresh data — reopening a card immediately after editing it could show the pre-edit value until an unrelated re-render happened to occur. Fixed by re-deriving both `items` and `selected` during render (React's recommended prop-sync pattern, avoiding an extra effect-triggered render pass) whenever a new `applications` prop arrives.

### Tech stack

Next.js (App Router) + TypeScript + Tailwind CSS + shadcn/ui + React Hook Form + Zod + TanStack Query on the frontend; Next.js Route Handlers + a `server/` service/repository layer on the backend; PostgreSQL + Prisma; Auth.js for authentication; a provider-agnostic `AIService` abstraction in `lib/ai/` (default provider: Anthropic) so the AI backend can be swapped without touching feature code.

### App folder structure

```
app/            Next.js App Router pages + app/api/** route handlers (REST API)
components/     ui/, dashboard/, resume/, jobs/, applications/, interviews/, copilot/
lib/            auth/, ai/, database/, validation/, storage/, utilities/
server/         services/, repositories/, controllers/  — business logic lives here, not in components
prisma/         schema.prisma, migrations/, seed.ts
types/, hooks/, tests/
```

Keep business logic out of UI components — components call `server/services`, services call `server/repositories`, repositories talk to Prisma.

### Rules specific to this app

- Never call the AI provider or hit the database directly from client components — always go through `server/services`.
- Never fabricate user experience, education, or qualifications in AI-generated content (resumes, cover letters); if required info is missing, say what's missing instead of inventing it.
- Every route handler validates input with Zod and re-checks auth/role server-side, even where middleware already gates the route.
- `AGENTS.md` in the project root is auto-generated/re-added by `next dev` (framework-version agent notes) — it is not this project's master config; **this file (`CLAUDE.md`) is**.
